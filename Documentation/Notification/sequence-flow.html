Sequence Flow - Notification Feature

Back to Main Documentation

Overview

This document outlines the typical sequence of interactions and data flow for the notification feature within the FMS system. The FMS notification system follows a condition-driven pattern where notifications are primarily triggered by specific events or conditions being met, rather than manual user actions.

Key Scenarios

Scenario 1: Condition-Triggered Notification (Primary Pattern)

System/Device -> FMS Backend: Monitoring data (tank levels, device status, health checks)
FMS Backend -> AlarmHandlerService: Evaluates trigger conditions
AlarmHandlerService -> AlarmHandlerService: Checks cooldown periods, daily limits, scope matching
AlarmHandlerService -> NotificationService: Creates CreateNotificationRequest if conditions met
NotificationService -> NotificationRecipientResolver: Resolves recipients based on policies/groups
NotificationRecipientResolver -> FMS.Persistence: Queries user preferences, site admins, policy recipients
NotificationRecipientResolver --> NotificationService: Returns resolved recipient list
NotificationService -> FMS.Persistence: Saves Notification entity and NotificationRecipient records
NotificationService -> FMS.BackgroundServices.NotificationProcessor: Publishes notification event
FMS.BackgroundServices.NotificationProcessor -> FMS.WebClient.NotificationHub: Sends real-time notification via SignalR
FMS.WebClient.NotificationHub -> FMS.frontend: Broadcasts notification to connected clients
FMS.frontend -> User: Displays notification (toast, badge, alert)

Scenario 2: Alarm-Based Trigger Example (Tank Low Volume)

Tank Monitoring System -> FMS Backend: Sends tank measurement data
FMS Backend -> AlarmHandlerService: ProcessTankMeasurement(tankId, measurement)
AlarmHandlerService -> AlarmHandlerService: Evaluates if ProductVolume < LowVolumeThreshold
AlarmHandlerService -> AlarmHandlerService: Checks AlarmHandler cooldown period
AlarmHandlerService -> NotificationService: TriggerLowVolumeAlarmAsync(tank, measurement)
NotificationService -> NotificationService: Creates CreateAlarmNotificationRequest
NotificationService -> NotificationRecipientResolver: Resolves site admin + policy recipients
NotificationService -> FMS.Persistence: Saves alarm notification with tank context
NotificationService -> SignalR Hub: Broadcasts critical tank alert
SignalR Hub -> FMS.frontend: Real-time notification to operations dashboard
FMS.frontend -> Operations Staff: Critical tank level alert with tank details

Scenario 3: Background Service Health Monitoring

Background Service -> Background Service: Periodic health check or reconciliation cycle
Background Service -> Background Service: Detects failure condition (e.g., high failure rate ≥50%)
Background Service -> NotificationService: SendSystemHealthNotificationIfNeeded()
NotificationService -> NotificationService: Creates CreateNotificationRequest with high priority
NotificationService -> NotificationRecipientResolver: Resolves system administrators
NotificationService -> FMS.Persistence: Saves system health alert notification
NotificationService -> SignalR Hub: Broadcasts system alert
SignalR Hub -> FMS.frontend: Admin dashboard alert
FMS.frontend -> System Administrators: Critical system health notification

Scenario 4: User Interacts with Notification (Mark as Read)

User -> FMS.frontend: Clicks 'Mark as Read' on a notification
FMS.frontend -> FMS.WebClient.NotificationController: Sends API request (e.g., PUT /api/notifications/{id}/read)
FMS.WebClient.NotificationController -> FMS.Application.Command.MarkNotificationAsReadCommand: Dispatches command
FMS.Application.Command.MarkNotificationAsReadCommand -> FMS.Application.Handlers.MarkNotificationAsReadCommandHandler: Handles command
FMS.Application.Handlers.MarkNotificationAsReadCommandHandler -> FMS.Persistence: Updates Notification entity status in database
FMS.Persistence --> FMS.Application.Handlers.MarkNotificationAsReadCommandHandler: Confirmation
FMS.Application.Handlers.MarkNotificationAsReadCommandHandler --> FMS.WebClient.NotificationController: Returns success
FMS.WebClient.NotificationController --> FMS.frontend: Returns API response
FMS.frontend -> User: Updates UI (e.g., removes notification, changes styling)

Scenario 5: Notification Group Management

User -> FMS.frontend: Navigates to Notification Group management page
FMS.frontend -> FMS.WebClient.NotificationGroupController: Requests list of notification groups (e.g., GET /api/notificationgroups)
FMS.WebClient.NotificationGroupController -> FMS.Application.Queries.GetNotificationGroupsQuery: Dispatches query
FMS.Application.Queries.GetNotificationGroupsQuery -> FMS.Persistence: Retrieves NotificationGroup entities
FMS.Persistence --> FMS.Application.Queries.GetNotificationGroupsQuery: Returns data
FMS.Application.Queries.GetNotificationGroupsQuery --> FMS.WebClient.NotificationGroupController: Returns data
FMS.WebClient.NotificationGroupController --> FMS.frontend: Returns API response
FMS.frontend -> User: Displays list of notification groups
User -> FMS.frontend: Creates/Updates/Deletes a notification group
FMS.frontend -> FMS.WebClient.NotificationGroupController: Sends API request (e.g., POST /api/notificationgroups)
FMS.WebClient.NotificationGroupController -> FMS.Application.Command.CreateNotificationGroupCommand: Dispatches command
FMS.Application.Command.CreateNotificationGroupCommand -> FMS.Persistence: Saves/Updates/Deletes NotificationGroup entity
FMS.Persistence --> FMS.Application.Command.CreateNotificationGroupCommand: Confirmation
FMS.Application.Command.CreateNotificationGroupCommand --> FMS.WebClient.NotificationGroupController: Returns success
FMS.WebClient.NotificationGroupController --> FMS.frontend: Returns API response
FMS.frontend -> User: Updates UI with changes
