🔧 Internal Business Function Notifications

End-to-End Tracking Without NotificationPolicy → Direct Service Integration → Notification Creation & Delivery

🆚 Key Difference: Policy-Based vs Internal Business Function Notifications

📋 Policy-Based Notifications

  • 🎯 Trigger: AlarmHandler + NotificationPolicy rules
  • 📊 Logic: JSON-based conditions evaluation
  • 🔄 Processing: PolicyRulesProcessor → recipient resolution
  • ⚙️ Example: Tank level < 10% → Send to managers

🔧 Internal Business Function Notifications

  • ⚡ Trigger: Business logic execution directly
  • 🎯 Logic: Hardcoded business rules in services
  • 🚀 Processing: Direct NotificationService call
  • ⚙️ Example: Stock reconciliation variance → Send to operators

🎯 Internal Business Function Flow Overview

Business Function Execution → Condition Evaluation → Direct Notification Creation → Recipient Resolution → Delivery & Tracking

📊 End-to-End Tracking & Storage

✅ How Internal Notifications Are Tracked

  1. Notification Entity: Stored with TriggerSource identifying business function
  2. No Policy Association: NotificationPolicyId = null
  3. Business Context: SiteId, TankId, VehicleId for contextual filtering
  4. Delivery Tracking: NotificationRecipient records for each delivery method
  5. Status Monitoring: Standard status tracking (Pending → Sent → Delivered)
Tracking Field Policy-Based Value Internal Business Function Value Purpose
TriggerSource "Alarm", "AlarmHandler" "ClosingStock", "AutomatedReconciliation", etc. Identifies notification origin
NotificationPolicyId Valid Policy ID (123, 456, etc.) null Links to governing policy
AlarmId Valid Alarm ID null Links to triggering alarm
TriggeredBy "System" or User ID "System" Identifies trigger initiator
Recipients Policy-resolved recipients Hardcoded or business-logic recipients Delivery target list

👥 Recipient Resolution for Internal Notifications

🎯 Internal Business Function Recipient Strategy

Since internal notifications don't use NotificationPolicy rules, recipients are determined by:

  1. Hardcoded Recipients: Business logic specifies specific roles/users
  2. Contextual Recipients: Site managers, tank operators based on context
  3. Severity-Based Recipients: Different recipients based on severity level
  4. Fallback Recipients: System administrators for critical errors

Example: Closing Stock Discrepancy Recipient Logic

// In ClosingStockCommandHandler.SendDiscrepancyNotificationAsync()
var recipients = new List<CreateNotificationRecipientRequest>();

// Base recipient: site manager
recipients.Add(new CreateNotificationRecipientRequest {
    UserId = "site-manager",
    DeliveryMethods = new List<string> { "System", "Email" }
});

// High severity: Add additional recipients
if (severity == DiscrepancySeverity.High) {
    recipients.Add(new CreateNotificationRecipientRequest {
        UserId = "area-supervisor",
        DeliveryMethods = new List<string> { "System", "Email", "SMS" }
    });
}

// Critical severity: Add regional manager
if (severity == DiscrepancySeverity.Critical) {
    recipients.Add(new CreateNotificationRecipientRequest {
        UserId = "regional-manager",
        DeliveryMethods = new List<string> { "System", "Email", "SMS", "Push" }
    });
}

Recipient Rules ✅ Dynamic recipient resolution via JSON ❌ Hardcoded recipient logic
Escalation ✅ Configurable escalation levels ❌ No automatic escalation

Processing Speed ⚠️ Additional policy evaluation overhead ✅ Direct notification creation

Tracking ✅ Full policy execution tracking ✅ Standard notification tracking

📈 Monitoring & Analytics

📊 Monitoring Internal Business Function Notifications

Key Queries for Analysis:

-- Count notifications by trigger source
SELECT TriggerSource, COUNT(*) as NotificationCount
FROM Notifications
WHERE CreatedAt >= DATEADD(day, -7, GETDATE())
  AND NotificationPolicyId IS NULL  -- Internal notifications only
GROUP BY TriggerSource
ORDER BY NotificationCount DESC;

-- Business function error rate
SELECT TriggerSource,
       COUNT(CASE WHEN Status = 'Failed' THEN 1 END) as FailedCount,
       COUNT(*) as TotalCount,
       (COUNT(CASE WHEN Status = 'Failed' THEN 1 END) * 100.0 / COUNT(*)) as FailureRate
FROM Notifications
WHERE TriggerSource IN ('ClosingStock', 'AutomatedReconciliation', 'DiscrepancyDetection')
  AND CreatedAt >= DATEADD(day, -30, GETDATE())
GROUP BY TriggerSource;

-- Critical system notifications
SELECT * FROM Notifications
WHERE TriggerSource LIKE '%Automated%'
  AND Priority = 'Critical'
  AND CreatedAt >= DATEADD(day, -7, GETDATE())
ORDER BY CreatedAt DESC;

🔧 Troubleshooting Internal Notifications

❌ Common Issues

  • No Notifications Generated: Check business function execution logs
  • Wrong Recipients: Review hardcoded recipient logic in services
  • Delivery Failures: Check NotificationRecipient.DeliveryStatus
  • Duplicate Notifications: Business functions may lack cooldown logic

✅ Debugging Steps

  1. Check service logs for business function execution
  2. Verify notification creation in Notifications table
  3. Check TriggerSource field to identify origin
  4. Review NotificationRecipient records for delivery status
  5. Monitor delivery channel logs (Email, SMS, etc.)
