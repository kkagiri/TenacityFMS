Notification Trigger Patterns

Back to Main Documentation

Overview

The FMS notification system follows a condition-driven pattern where notifications are primarily triggered by specific events or conditions being met. This document outlines the primary trigger patterns and their implementations.

Primary Flow:
Condition Met → AlarmHandlerService/BackgroundService → CreateNotificationRequest → NotificationService → Recipients Resolution → Delivery

Primary Trigger Patterns

1. Alarm-Based Triggers (Most Common)

These are the most frequent notification triggers in the system, monitoring critical operational conditions.

Tank Level Conditions

  • Low Volume Alarms: Triggered when tank product volume falls below defined thresholds
  • High Volume Alarms: Triggered when tank reaches maximum capacity limits
  • Water Detection: Alerts when water contamination is detected in fuel tanks
  • Temperature Anomalies: Notifications for abnormal temperature readings
Example Implementation:
AlarmHandlerService.TriggerLowVolumeAlarmAsync()
Condition: tank.ProductVolume < tank.LowVolumeThreshold
Result: Creates alarm notification with tank details and site information

Device Alarms

  • PTS Device Failures: Point-of-sale terminal malfunctions or communication errors
  • Pump Issues: Fuel dispenser operational problems
  • Probe Malfunctions: Tank monitoring equipment failures
Example Implementation:
NotificationService.CreatePTSAlarmNotificationAsync()
Condition: PTS device communication timeout or error response
Result: Device-specific alarm with location and error details

Policy-Based Alarms

  • Configurable Thresholds: User-defined conditions using AlarmHandlers
  • Cooldown Management: Prevents notification spam with configurable intervals
  • Daily Limits: Maximum notifications per day per handler
  • Site/Tank Scoping: Conditions applied to specific locations or equipment
Example Implementation:
AlarmHandlerService.ProcessGenericAlarmAsync()
Condition: EvaluateTriggerConditions(handler.TriggerConditions, event)
Result: Policy-defined notification with template-based messaging

2. Background Service Triggers

Automated monitoring services that continuously check system health and operational status.

System Health Monitoring

  • Service Failures: Background service startup/shutdown notifications
  • Configuration Errors: Invalid service configurations or missing dependencies
  • Health Checks: Periodic system health verification failures
Example Services:
• PolicyTriggerBackgroundService - Redis event processing
• NotificationBackgroundService - Scheduled notification processing
• AutomatedReconciliationBackgroundService - Data consistency checks

Reconciliation Issues

  • High Failure Rates: When reconciliation processes fail above threshold (≥50%)
  • Data Discrepancies: Inconsistencies found during automated checks
  • Processing Errors: Failures in background data processing tasks
Example Implementation:
AutomatedReconciliationBackgroundService.SendSystemHealthNotificationIfNeeded()
Condition: failureRate >= 0.5 && processedPolicies > 0
Result: High-priority system health alert

Scheduled Checks

  • Automated Monitoring Cycles: Regular system checks (every 1-5 minutes)
  • Maintenance Windows: Scheduled maintenance and update notifications
  • Periodic Reports: Scheduled summary notifications

3. Business Logic Triggers

Notifications triggered by specific business process events and validation failures.

Issue Tracker Events

  • Problem Escalations: Issues requiring management attention
  • Status Changes: Updates to issue resolution progress
  • Assignment Changes: Issue ownership transfers
Example Implementation:
NotificationService.CreateIssueTrackerNotificationAsync()
Condition: Issue status change or escalation trigger
Result: Stakeholder notification with issue details and actions required

Data Validation

  • Invalid Configurations: System setup or parameter validation failures
  • Missing Data: Required information not provided or corrupted
  • Compliance Violations: Regulatory or business rule violations

Notification Creation Flow

Detailed Trigger Flow:

1. Condition Detection
├── Tank measurement ingestion
├── Device status monitoring
├── Background service health checks
└── Business process validation

2. Trigger Evaluation
├── AlarmHandlerService.EvaluateTriggerConditions()
├── Policy matching (site, tank, device scope)
├── Cooldown period checking
└── Daily limit validation

3. Notification Creation
├── CreateNotificationRequest assembly
├── Template message formatting
├── Priority assignment
└── Metadata collection

4. Recipient Resolution
├── Policy-based recipients
├── Site administrator lookup
├── User subscription preferences
└── Fallback recipient handling

5. Delivery Processing
├── Multi-channel delivery (Email, SMS, System)
├── Delivery status tracking
├── Real-time SignalR notifications
└── Audit trail creation

Configuration and Customization

AlarmHandler Configuration

The system uses AlarmHandlers to define configurable trigger conditions:

  • TriggerConditions: JSON configuration defining when to trigger
  • Scope Filtering: Site, Tank, or Device-specific conditions
  • Rate Limiting: Cooldown periods and daily notification caps
  • Message Templates: Customizable notification content
  • Priority Levels: Critical, High, Medium, Low priorities

Notification Policies

Policies control how notifications are processed and delivered:

  • Channel Configuration: Enable/disable Email, SMS, System notifications
  • Recipient Groups: Define who receives specific notification types
  • Delivery Preferences: User-specific notification settings
  • Escalation Rules: Automatic escalation for unacknowledged critical alerts

Integration Points

Key services and components involved in the trigger system:

  • AlarmHandlerService: Primary alarm condition evaluation
  • NotificationService: Central notification creation and management
  • NotificationRecipientResolver: Dynamic recipient determination
  • Background Services: Automated monitoring and health checks
  • SignalR Hub: Real-time notification delivery
  • Email/SMS Services: External communication channels
