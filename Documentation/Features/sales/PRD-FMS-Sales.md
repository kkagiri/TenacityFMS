# PRD — FMS.Sales (Subscription, Billing & Sales)

**Version:** V1
**Status:** Active scaffolding (database migrated, projects build clean)
**Owner:** Platform / Sales
**Last updated:** 2026-04-29

---

## 1. Purpose

FMS.Sales is a **separate bounded context** that owns the commercial side of the
Tenacity FMS platform: plans, pricing (multi-currency), subscriptions, quotas,
usage metering, invoicing, payments (Stripe + manual), onboarding requests,
coupons, and a sales audit trail.

It is physically separated from the main FMS application so that commercial
concerns can evolve independently of operational fleet management features.

---

## 2. Architectural Principles

| Principle            | Decision                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Isolation of code    | Separate solution `FMS.Sales.sln` with 4 projects (`Domain`, `Application`, `Persistence`, `Api`).                  |
| Database             | **Shared PostgreSQL database** (`tenacy_fms`) — Sales tables prefixed `sales_*` to avoid collisions.                |
| Schema ownership     | Only `FMS.Sales.Persistence` migrates `sales_*` tables. The main FMS DbContext must NOT include any Sales entities. |
| Cross-context reads  | Main FMS reads `sales_subscription` / `sales_plan_quota` via a thin read-only adapter (no writes).                  |
| Cross-context writes | Main FMS never writes to `sales_*` tables. All mutations go through FMS.Sales.Api.                                  |
| Stability guarantee  | Changes inside FMS.Sales must NOT break the main system. Public contracts (table shape + Api routes) are versioned. |
| Tenant model         | Subscriptions belong to a `tenant_id` matching the main FMS tenant.                                                 |

## 3. Pricing Model — Hybrid Option 3 (selected)

The platform sells **plans with included quotas + metered overages** in
**multiple currencies**.

### 3.1 Plans (current seeds)

| Code       | Name       | Monthly USD | Annual USD | Sites | Users | Vehicles | RFID | PTS pumps | Tank sensors |
| ---------- | ---------- | ----------- | ---------- | ----- | ----- | -------- | ---- | --------- | ------------ |
| starter    | Starter    | 99          | 990        | 1     | 5     | 25       | 50   | 2         | 4            |
| growth     | Growth     | 299         | 2,990      | 3     | 20    | 100      | 250  | 8         | 16           |
| pro        | Pro        | 599         | 5,990      | 10    | 75    | 500      | 1000 | 25        | 50           |
| enterprise | Enterprise | custom      | custom     | ∞     | ∞     | ∞        | ∞    | ∞         | ∞            |

### 3.2 Overage units (metered)

- additional vehicle / month
- additional user / month
- additional site / month
- additional RFID tag
- additional PTS pump
- additional tank sensor
- API call beyond quota (per 1k)

### 3.3 Multi-currency

All prices are stored per (`plan_id`, `currency_code`) in `sales_plan_price`.
`sales_currency` holds ISO 4217 code, symbol, decimal places, and a
**reference FX rate to USD** (informational; we do not auto-convert at billing
time — each invoice locks to the price book entry that was active when the
subscription was created).

Default supported currencies: USD, EUR, GBP, AUD, CAD, AED, SGD, INR, IDR, MYR.

## 4. Acquisition Channels

### 4.1 Self-serve onboarding (primary)

1. Prospect submits `sales_onboarding_request` (company, contact, country,
   chosen plan, currency).
2. System creates a **trial** `sales_subscription` (`status = Trial`,
   `payment_provider = Stripe`).
3. After trial → Stripe Checkout collects payment method → subscription becomes
   `Active`.
4. Stripe webhooks update `sales_invoice` and `sales_payment`.

### 4.2 Manual sales (assisted)

For enterprise / large regional deals where Stripe is not used (POs, bank
transfer, local invoicing requirements).

1. Sales rep creates `sales_manual_sale` (quoted amount, currency, terms).
2. On approval the system creates a `sales_subscription` with
   `payment_provider = Manual`.
3. Invoices (`sales_invoice`) are generated by FMS.Sales but settlement is
   recorded by Sales staff via `sales_payment` rows referencing external
   bank / PO numbers and uploaded proof.
4. Audit trail in `sales_audit_log`.

## 6. Public Contracts

### 6.1 Database read contract (consumed by main FMS)

Main FMS may **read** the following columns only:

- `sales_subscription`: `tenant_id`, `plan_id`, `status`, `current_period_end`.
- `sales_plan`: `id`, `code`, `name`.
- `sales_plan_quota`: `plan_id`, `metric_key`, `included_quantity`.

These columns are considered the stable contract. Renames require a
deprecation cycle with a backfill view kept for 1 minor version.

### 6.2 HTTP API (FMS.Sales.Api — versioned `/api/v1/sales/...`)

Initial surface (to be implemented next):

- `GET  /plans` — public plan catalog (per currency).
- `GET  /currencies` — supported currencies.
- `POST /onboarding` — submit onboarding request.
- `GET  /subscriptions/me` — current tenant’s subscription + usage snapshot.
- `POST /subscriptions/checkout` — create Stripe Checkout session.
- `POST /webhooks/stripe` — Stripe event sink (idempotent).
- `POST /admin/manual-sales` — internal admin: create manual sale.
- `POST /admin/manual-sales/{id}/win` — convert manual sale → subscription.
- `POST /admin/payments/manual` — internal admin: record manual payment.

All admin routes require role `SalesAdmin` issued by the main IdP and presented
as a JWT.

## 7. Quota Enforcement Flow

1. Main FMS performs an action (e.g. create vehicle).
2. Main FMS calls **read-only** quota helper: `SELECT included_quantity FROM
sales_plan_quota WHERE plan_id = ? AND metric_key = 'vehicles'` joined to
   the tenant’s active `sales_subscription`.
3. Main FMS counts current entities for the tenant (its own DbContext, with
   `IgnoreQueryFilters` so the tenant filter doesn’t recurse).
4. If `current >= included`, the main FMS may either:
   - Block (hard quota) — for the free / trial plans.
   - Allow + record overage (soft quota) — FMS.Sales meters it on the next
     usage roll-up.

Daily roll-up: a hosted service in FMS.Sales.Api scans tenants and writes
`sales_usage_record` rows.

## 8. Stripe Integration (Phase 2)

- One Stripe **Product** per plan code.
- One Stripe **Price** per (plan, currency, billing cycle).
- Webhook events handled (idempotent by `event.id`):
  `checkout.session.completed`,
  `invoice.paid`,
  `invoice.payment_failed`,
  `customer.subscription.updated`,
  `customer.subscription.deleted`.
- All webhook payloads stored raw in `sales_audit_log` for replay.

---

## 9. Manual Sales Flow (Phase 2)

1. Sales rep logs in to FMS.Sales admin UI.
2. Creates `sales_manual_sale` with: tenant (or pending tenant), plan,
   currency, custom price, term, contract reference, expected close date.
3. Status transitions: `Draft → Quoted → Won | Lost | Expired`.
4. On `Won`: subscription is created (`payment_provider = Manual`,
   `status = Active`), an invoice is generated, and Sales records the payment
   when funds clear.

## 11. Out of Scope for V1

- Tax engine integration (Avalara / TaxJar).
- Dunning automation.
- Partner / reseller billing.
- Usage-based AI / per-event pricing.
- Multi-entity invoicing (one tenant ↔ multiple legal entities).

## 12. Open Decisions

1. Does main FMS read `sales_*` directly (shared DbContext fragment) or only
   via Api? **Current direction:** read directly (shared DB), write only via
   Api. To revisit if cross-team contention emerges.
2. Where does `tenant_id` originate? **Direction:** `tenant_id` is minted by
   FMS.Sales onboarding and pushed to main FMS at first login.
3. FX policy on currency change — lock-on-create vs. re-quote at renewal.
   **Direction:** lock-on-create; re-quote at renewal only.
